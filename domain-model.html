01 — Purpose & authority

Domain Model v1 makes the product’s meaning explicit before technical architecture begins.

It records what ResuMate concepts mean, how they relate, which rules must not be broken, and which choices deliberately remain for later technical design.

It defines

Product meaning

Conceptual objects, ownership, relationships, lifecycle behavior, rules, edge cases, and MVP boundaries.

It does not define

Technical implementation

No database tables, API contracts, JSON schema, storage engine, agent boundaries, or rendering architecture are locked here.

Authority order

Explicit product truth wins

Latest product-owner decision → Domain Model Cross-Check → Research Foundation → external references → generic assumptions.

Source: Domain Model v1 §§0–1.

02 — Core conceptual model

A private account organizes independent Resumes, grouped by Version and Variation.

USER │ ├── User Profile (private account data) │ ├── Version 1 (standalone Resume) │ ├── Variation 1 │ ├── Variation 2 │ └── Variation N │ ├── Version 2 (standalone Resume) │ └── Variation 1 │ └── Active CV Selection (0..1) └── references one existing Version OR Variation PLATFORM └── Template Library (shared reusable presentation definitions)

A Version or Variation is a standalone Resume snapshot. Variations are grouped under one root Version; the UI stays flat even when internal provenance knows a Variation was created from another Variation.

Source: Domain Model v1 §2; §5.3; §29.

03 — Resume identities

Version and Variation are not cosmetic labels. Their creation rules define their identity.

Version

A distinct persisted base Resume entry

New creation, import/save, or explicit Duplicate Version creates a Version. Similarity does not merge independently created Resumes, and a Version can exist without Variations.

Variation

A saved branch from a persisted Resume

Tailoring, enhancement, ATS improvement, rewriting, or custom editing may produce a Variation only when the user saves that branch.

CREATE / IMPORTTemporary Working State
PREVIEWUser reviews content
SAVEPersisted Version
EDIT / TAILORNew Working State
SAVE BRANCHPersisted Variation
Position ≠ Variation. A Frontend role can have several Variations because Company A, B, and C describe different job contexts. A Variation can also exist without a position or JD.

Source: Domain Model v1 §§4–6, §19.

04 — Active CV model

Active CV is an optional user selection, not another Resume type or a public profile.

Cardinality

Zero or one

A personal user may have no Active CV, one Active Version, or one Active Variation.

Future role

Job-seeking context

Resume-building works without an Active CV. The selection mainly guides later job-seeking capabilities.

Deletion

No automatic replacement

Deleting the referenced Resume clears Active CV. ResuMate must not silently select another one.

“Possible outdated” is not determined by age alone. Newer relevant career evidence can trigger an explanation and recommendation, but the user decides whether to retain, edit, or replace the Active CV.

Source: Domain Model v1 §7.

05 — Snapshot ownership & lifecycle

Every persisted Resume owns its own content snapshot.

Domain Model v1 deliberately rejects a shared mutable Career Facts object. Editing one Resume must never silently change another Resume.

Resume-local content

  • Personal details
  • Education and work experience
  • Skills, projects, certifications, languages
  • Accepted AI-generated wording
  • Optional Job Context and selected Template

Ownership boundaries

  • User Profile is private account-operating data, not a career profile.
  • Account owner and Resume subject can be different people.
  • Duplicate Version has no future mutable link to its source.
  • Working State is temporary, not a persisted Resume entity.

Lifecycle is intentionally minimal: create/import → temporary working state → preview → save → persisted Resume. Archive, full revision history, and Trash/restore are future scope; MVP uses confirmed direct deletion.

Source: Domain Model v1 §§3, 4.3–4.6, 9, 18–20.

06 — Evidence & AI truth

AI may create professional narrative, but it cannot manufacture career evidence.

Evidence-like fields

  • Employer, position, and dates
  • Education and certification
  • Project identity and factual skills
  • Awards and measurable results

Narrative/presentation fields

  • Profile summary and experience description
  • Bullet wording and concise/expanded phrasing
  • Section ordering and emphasis
  • Professional writing based on supported evidence

Factual evidence fields must not be silently altered without user confirmation. When evidence is missing, ResuMate asks, flags a gap, or keeps the claim out—rather than inventing employers, skills, metrics, team sizes, projects, or achievements.

Source: Domain Model v1 §10; §22 invariants 5–6.

07 — Existing Resume import

Upload is an input. It becomes a Version only when the user saves or imports it.

Path Domain behavior Boundary
Use As-Is Original Resume is saved/registered as a Version in its chosen representation. The user keeps the original design; extraction can remain on demand for future features.
Structured import Content is extracted, reviewed, mapped, and rendered with a ResuMate Template before save. Arbitrary PDF/Word/Canva layouts are not promised pixel-perfect reconstruction.
Extract + enhance User reviews extracted values and may apply enhancements before first save. Uncertain values are flagged, not guessed.
Tailor later Persisted imported Version enters a Working State, then updates current or saves a Variation. The original import is not destructively overwritten by branching.

Unreadable, corrupted, password-protected, or unsupported input must not produce hallucinated content. Ask for a usable file or offer Form/Chat creation instead. Unknown meaningful sections become Custom Sections when no reliable mapping exists.

Source: Domain Model v1 §§11–14.

08 — Job Context

Job Context is optional, composable context for orienting or tailoring a Resume.

Broader direction

Target Role(s)

One or more roles that fit the Resume evidence, skills, experience, or intended direction.

Specific opportunity

Applied Position

A more particular position, commonly connected with a hiring opportunity. It is distinct from Target Role.

Supporting context

JD, requirements & more

Job description, requirements, company, location, employment type, or a complete hiring post can be provided in any combination.

AI may parse a hiring post and infer likely context when the title is missing, but the user can confirm or edit it. Job/Application records and auto-apply are future domains; v1 requires no forced auto-tailor or auto-apply behavior.

Source: Domain Model v1 §15.

09 — Template & localization

Templates render content; localization recommends context-aware presentation without deleting user data.

Template

A shared platform presentation definition

Structured Resume content plus a selected Template produces a rendered Resume. Switching Templates changes neither Version nor Variation and must not change content.

Localization

Contextual, not universal

Target market/region is primary, with user location and user override where relevant. Age, photo, NRC, passport, gender, and marital status are contextual—not universally mandatory.

If a Template cannot represent meaningful content or the recommended localized presentation, ResuMate warns, recommends, or adapts. It must not silently drop content. A Myanmar-oriented Version may be tailored into a Singapore/US-oriented Variation.

Source: Domain Model v1 §§16–17.

10 — Hard invariants

These rules are the model’s non-negotiable product boundaries.

ROOTEvery persisted Variation belongs to one root Version.
SNAPSHOTEditing one Resume cannot mutate another.
PRESENTATIONTemplate changes never alter Resume content.
TRUTHAI cannot fabricate unsupported career facts.
EVIDENCEFactual fields never silently change without confirmation.
ACTIVEActive CV references one valid existing Resume, or none.
PRIVACYUser Profile remains private.
IDENTITYNew/import/duplicate → Version; saved branch → Variation.
CONTROLAI output does not silently become persisted truth.

Source: Domain Model v1 §22.

11 — Edge cases & MVP boundary

The model protects simple MVP behavior while making later expansion possible.

Selected edge cases

Explicit behavior

  • No work experience does not block Resume creation.
  • 50+ Variations are conceptually allowed; subscription limits are business policy.
  • Root deletion can preserve Variations by promoting the oldest one to root.
  • Missing JD title can be inferred, then user-confirmed.
  • Missing skill becomes a visible gap, never a fake claim.
MVP restraint

Not in this domain build

  • Agency multi-client workflows
  • Portfolio implementation
  • Job Platform and Application Lifecycle
  • Custom Template builder
  • Trash/restore and full revision history

Current domain foundation

  • Private User/Profile
  • Form, AI/Chat, and import creation
  • Use As-Is, extraction/review, enhance, tailor
  • Version / Variation snapshots
  • Active CV selection
  • Templates, localization, diagnostics

Later technical decisions

  • Database tables and JSON schema
  • Storage and rendering engine
  • API contracts and agent boundaries
  • AI memory and temporary-state mechanism
  • Tenant/Agency implementation strategy

Source: Domain Model v1 §§23, 25–26.
