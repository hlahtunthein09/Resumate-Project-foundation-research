RESUMATE · SYSTEM DESIGN V1 · STAGES 1–7

A technical review checkpoint before implementation.

A modular, AI-assisted Resume system designed for independent document snapshots, user-controlled AI changes, privacy, predictable output, and measured scaling.

LOCKED FOUNDATIONCANDIDATES REMAIN PROVISIONALSENIOR REVIEW REQUIRED

01 / Executive summary

Build a small, coherent system before adding distributed complexity.

ResuMate V1 is a modular monolith with a Node.js web process and worker process, managed PostgreSQL, private object storage, server-side PDF rendering, and an AI harness that proposes validated changes instead of mutating data.

SOURCE OF TRUTH

Application state

Resume snapshots and related persisted records reconstruct each operation’s context. Models retain no application memory.

DOCUMENT INTEGRITY

Independent snapshots

Version and Variation can share one entity shape, but changing one must never mutate another.

OPERATING PRINCIPLE

Measure, then scale

Start with the simplest practical topology and add queues, caches, indexes, or services only for measured needs.

Application owns context. Models do not own context.

03 / Domain & data model

Relational metadata carries identity and access patterns; JSONB carries the Resume document.

Version / Variation relationship

→
VARIATION`rootVersionId` identifies the group; `sourceResumeId` captures direct lineage.
→
Variation A · job tailoring
Variation B · AI enhancement
Variation C · alternate context

Working Draft

Single server-backed recovery/editing state; debounced full snapshot autosave; not a persisted Resume lifecycle type.

Original File

Private object bytes plus metadata such as storage key, MIME type, checksum, size, and filename.

Public Profile snapshot

Published output is a separate snapshot. Private Resume edits never silently alter the public page.

Source boundary: Resume structured JSON is authoritative document state. A generated PDF is a short-lived derived artifact, never the Resume source of truth.
Persistence and cross-device integrity
Stable section, block, and item IDs support patches, reordering, validation, diffs, and undo/redo. Each persisted Resume carries a revision; writes send expectedRevision and stale updates are rejected rather than automatically merged. V1 reloads the newest server version after a cross-device conflict. Direct Edit updates only the current Resume; full revision history is future scope. Active CV is a separate user-level selection, and root deletion that preserves Variations transactionally promotes the oldest preserved Variation to root Version.

05 / AI architecture

AI is a validated proposal pipeline, not a privileged writer to application data.

AI Harness flow

User instructionRewrite, analysis, tailoring, or document operation.
→
Task router + context builderLeast-context principle; only task-relevant Resume and Job Context.
Prompt / tool contractStable rules and schemas before dynamic context.
→
Structured outputSchema validation → business/evidence validation → ProposedPatch.
User decisionPreview → Accept / Edit / Reject → apply to Working Draft only.
TRUTH RULE

Evidence beats fluent wording

AI may transform supported facts but must never create unsupported employers, dates, qualifications, skills, projects, metrics, or achievements.

MODEL ROUTING

Quality threshold before price

Task classes select the cheapest model that reliably meets factual, structured-output, relevance, latency, and quality needs.

AI may not fabricate unsupported career evidence.
AI execution boundaries
Valid operations from a partial AI failure may still be previewed when another operation is invalid. Users can cancel long work; ResuMate marks the job cancelled, attempts provider abort where supported, and ignores late results. Analysis caching keys include Resume content hash, Job Context hash, analysis version + model/config version. Stable instructions and schemas are ordered before dynamic context for prompt caching readiness.

07 / Security

Private data is protected by authentication plus resource-level authorization.

AUTHENTICATION

Who is the user?

Private resource access begins with a signed-in user; V1 direction supports email/password and Google OAuth.

AUTHORIZATION

Do they own this resource?

Knowing a record ID grants nothing. The server enforces ownership for every private Resume, draft, file, job, and context record.

AI MINIMIZATION

Send only required context

A work-description rewrite needs relevant career facts, not passport data, home address, or unrelated personal fields.

Classification Examples Default handling
Sensitive NRC, passport, DOB, phone, address, original CV Private; never routine production-log content
Private Resume, Working Draft, Job Context, unpublished analysis Authentication + ownership authorization
Public Only user-approved published snapshot fields Anonymous route allowed solely for the published profile
Additional controls
Allow only PDF, DOCX, JPG, JPEG, and PNG. Validate extension, MIME type, magic bytes, size, ownership, random key, private-object state, and signed-URL expiry. Use rate limits plus quotas for AI, and separate abuse limits for uploads, exports, password reset, public profile, and expensive processing.
Security operations still required
Malware scanning follows a maturity path: validation and private storage first, scanner integration readiness next, then scanning before wider public scale. Secrets separation requires distinct development, staging, and production credentials; production secrets must never be committed to Git.

08 / Reliability & failure design

Dependency failures degrade the affected capability without unnecessarily taking down the Resume workflow.

AI unavailable

Open, edit, save, Version/Variation management, and Public Profile remain where possible; AI functions become unavailable.

OCR unavailable

Digital PDF/DOCX parsing can continue; scanned inputs receive retry or manual-entry routes.

Storage unavailable

Upload/download/original access suffers, while structured Resume editing and saving should remain usable where possible.

JOB FAILURE

Limited retry, backoff, jitter

Retry only transient failures. Permanent validation, auth, and deterministic bad-request failures must not loop indefinitely.

DATA RECOVERY

Backups + PITR + restore drills

Target RPO is as close to zero as practical, ≤ 1 hour. Target RTO is a few hours. PITR should be enabled from production launch if cost is reasonable. Restore drills may be monthly/manual and around major high-risk releases.

Operational failure controls
Pending uploads are cleaned by scheduled/lifecycle policy. V1 uses distinct timeout classes for normal API calls, small AI work, full AI jobs, OCR, and PDF rendering. Before risky migrations or major releases: verify backup/recovery, migrate, health-check, and keep a rollback path.

LOAD ASSUMPTIONS

25 → 100 concurrent

Initial baseline: 25 active users. Success scenario: 100 concurrent users, with a realistic mix rather than 100 full tailoring jobs.

METRICS

p95, error rate, throughput

Measure dashboard, editor, autosave, public profile, upload, job creation, and PDF paths separately as implementation data arrives.

CACHE BOUNDARY

Never cache authority

Editable Resume and Working Draft stay authoritative in PostgreSQL plus client state. CDN/HTTP caching suits the published snapshot.

Durable queue trigger criteria
Evaluate Redis/BullMQ/managed queue when jobs are lost, workers race, DB polling is expensive, backlog is persistent, retries are difficult, priority queues are needed, or distributed coordination becomes necessary. Before that, ProcessingJob + worker abstraction remains sufficient.
DATABASE DISCIPLINE

Keep dashboard reads lightweight

Dashboard cards fetch metadata, counts, active state, target role summary, timestamps, and pagination—not full Resume JSON. JSONB exists ≠ a day-one index requirement: no day-one JSONB GIN index. Indexes follow measured slow-query evidence and EXPLAIN ANALYZE.

WORKER CLASSES

Separate AI / OCR / PDF concurrency

Bounded database pools and separate concurrency limits are benchmarked for AI waits, CPU/GPU OCR, and headless-browser PDF work. Horizontal scaling re-evaluates the database connection budget.

12 / Risks

Known risks have boundaries and operating responses, not hidden assumptions.

AI cost growth

Track cost per user and operation; enforce quotas, output limits, routing evaluation, and spending review.

Truth boundary

Structured output, evidence validation, ProposedPatch preview, and user approval contain hallucination risk.

Extraction + render quality

Parser-first/OCR fallback, confidence review, and shared preview/export behavior reduce mismatch.

Operational load

Backpressure, job status, bounded worker classes, backups, and gradual infrastructure complexity fit a small team.

Cross-device conflict

Revision checks reject stale writes instead of silently merging concurrent edits; the user reloads the newest server version after a cross-device conflict.

Sensitive-data leakage

Ownership authorization, private objects, least-context AI, and a no-raw-Resume logging policy constrain sensitive-data leakage exposure risk.
